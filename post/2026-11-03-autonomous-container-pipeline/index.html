Beyond the IDE: Running Autonomous Agentic SDLC in Isolated Containers

In Part 1 and Part 2, I shared the governance rules that keep AI coding agents on track: Dual-PR Spec-First contracts and the adaptive L0–L3 auto mode.

However, one practical problem remained: everything still runs on the developer’s laptop.

If an agent needs 10 minutes to run tests, explore AST files, and do a review pass, the developer has to keep their laptop awake, avoid switching branches, and baby-sit terminal prompts. If you try to run agents in standard CI, they either crash when asking for interactive input or make wild guesses.

I wanted to take this entire workflow off developer machines and move it into an ephemeral, hardened container running in the background (asdlc run --container).

With the container design now finalized in agentic-sdlc, this post explains how the architecture works, how it handles human PR reviews without a terminal, and the trade-offs I made.

🎯 BLUF (Bottom Line Up Front)

  • The Goal: Run the Agentic SDLC lifecycle unattended in a non-root Linux container (ubuntu:26.04, UID 10001:10001), interacting with engineers strictly through Git and GitHub PR comments.
  • The “3+1” Stage Model: Instead of a “black box” that guesses what to do across days, the pipeline uses four clear stages: --stage spec (drafting and linting), --stage apply (TDD loop), --stage verify (14 quality gates and review), and --stage fix (autonomous review comment fixes).
  • Async PR Comment Grilling: If requirements are unclear, the container opens a Draft Spec PR, posts questions in a PR comment, and shuts down immediately (zero idle compute cost). When a human replies on GitHub, re-running the command ingests the answers and moves forward.
  • 3-Tier PR Review Triage: When colleagues leave review comments, --stage fix automatically classifies them into: code fixes (applies edits and reruns tests), technical questions (answers from design.md without editing code), and scope creep (politely defers to another issue).
  • Dual-Track Symmetry: The container mode does not break or replace the local IDE workflow. Both share the exact same Git repository and OpenSpec files as the single source of truth.

1. Why Running Agents on Laptops Doesn’t Scale

Watching tools like VS Code + Claude Code or terminal CLI agents write code in real time looks great in demos. But in real team workflows, running autonomous agents locally hits four clear walls:

  1. Terminal Babysitting: A full TDD loop and multi-round review often take 5 to 15 minutes. Developers have to keep their laptops open and wait.
  2. Workspace Contamination: Agents create build caches, temporary test files, and sometimes leave dirty Git state or mess up line endings (CRLF vs. LF on Windows).
  3. Complex Input: Real requirements don’t come as a short CLI string like asdlc new "Fix payment retry". They come as Jira tickets, Figma links, and multi-page PRDs.
  4. No TTY in Headless Mode: When an agent hits an unclear requirement, it prompts the user on standard input (stdin). In headless cloud runners with no TTY, this either crashes or forces the agent to hallucinate an answer.

To make agentic coding practical at scale, the agent loop must move into an isolated container runtime.

3. The “3+1” Canonical Stage Execution Model

A common mistake in autonomous coding tools is trying to build a “magic black box” that runs from start to finish without human touchpoints.

In real teams, software delivery is naturally staged and asynchronous. You write a spec, wait for review, get approval, write code, get another review, and merge.

Instead of guessing state, agentic-sdlc uses Bounded Stage-Driven Execution:

                       THE "3+1" CANONICAL STAGES
 ┌──────────────────────┐  ┌──────────────────────┐  ┌──────────────────────┐
 │ 1. --stage spec      │  │ 2. --stage apply     │  │ 3. --stage verify    │
 ├──────────────────────┤  ├──────────────────────┤  ├──────────────────────┤
 │ Intake, AST explore, │  │ Task authoring and   │  │ 14 quality gates and │
 │ spec drafting, AI    │  │ task-level TDD Red-  │  │ independent review;  │
 │ review & Ready Spec PR│ │ Green loop (0444 lock)│ │ opens Impl PR        │
 └──────────────────────┘  └──────────────────────┘  └──────────────────────┘
                                      │
                         ┌────────────▼───────────┐
                         │   +1. --stage fix      │
                         ├────────────────────────┤
                         │ Autonomous triage and  │
                         │ resolution of human PR │
                         │ review comment threads │
                         └────────────────────────┘
  1. Bounded Execution: Inside each run, the container does its job automatically (TDD loop, gate checks, review comment handling).
  2. Clear Milestones: Between stages, the container stops and waits for human action on GitHub.
  3. Zero Idle Compute: When a stage finishes or hits a question, the container destroys itself (--rm). It never sits idle waiting for someone to type.

4. Handling Review Comments Without a Terminal (--stage fix)

One common headache with automated coding is: what happens when human colleagues leave comments on a PR?

Reviewers often don’t click GitHub’s formal “Request Changes” button. They leave inline questions, suggest renames, or ask why a certain library was chosen.

When you run asdlc run #42 --stage fix, the container uses a 3-Tier Triage Engine:

  flowchart TD
    THREAD["Unresolved PR Review Thread (via GraphQL)"] --> CLASSIFY{"Review Comment Triage Engine"}

    CLASSIFY -->|Tier 1: Concrete Suggestion / Bug| T1["<b>Tier 1: Code Fix</b><br/>• Apply GitHub suggestion or code edit<br/>• Re-run unit tests &amp; asdlc verify<br/>• Push fix commit &amp; resolve thread"]
    CLASSIFY -->|Tier 2: Technical Inquiry / Question| T2["<b>Tier 2: Technical Explanation</b><br/>• Extract rationale from design.md<br/>• Post inline reply in thread (Zero code edits)<br/>• Resolve thread"]
    CLASSIFY -->|Tier 3: Scope Creep / Out-of-Bounds| T3["<b>Tier 3: Scope Creep Deflection</b><br/>• Identify boundary expansion<br/>• Reply explaining spec scope bounds<br/>• Defer to separate tracking issue"]
  1. Tier 1 (Code Fixes & Suggestions): If a reviewer points out a bug, suggests a variable rename, or provides a GitHub suggestion block (````suggestion`), the agent updates the code, reruns the test suite, verifies all gates pass, commits, and resolves the thread.
  2. Tier 2 (Technical Questions): If a reviewer asks: “Why did you use Redis here instead of Caffeine cache?”, the agent does not touch the code. It reads design.md, writes a clear explanation as an inline reply, and resolves the thread.
  3. Tier 3 (Scope Creep): If a reviewer asks: “Can we also add export-to-Excel in this PR?”, the agent checks the locked spec. It politely replies that this is out of scope for the current change, suggests opening a new ticket, and resolves the thread.

6. Key Container Engineering Trade-offs

Building an isolated container runner brought up several technical trade-offs:

1. Ephemeral Internal Clone vs. Host -v Mounting

The simplest approach is mounting the local folder with docker run -v $(pwd):/workspace. I decided against this:

  • File I/O slow down: On Windows and macOS, bind mounts across virtualized file systems slow down build tools (npm, maven, pytest) by 5x to 10x.
  • Workspace pollution: Linux containers write Linux binary caches and symlinks into the host folder, often creating Git dirty state or CRLF line ending issues on Windows.
  • Decision: The container does a clean clone into internal ext4 /workspace. All code changes are pushed back via Git using temporary gh auth token credentials. The host directory stays completely clean.

2. Atomic Base Config vs. Recursive Config Mutation

How should container model settings combine with host AI configuration?

  • Mutating configuration files or trying to merge custom proxies, headers, and API keys often silently corrupts credentials.
  • Decision: Treat base configs as immutable units (copied as-is from host configs). If the container needs to use a specific model or provider (like an enterprise model instead of the developer’s default), pass it via runtime CLI flags and environment variables: 
    claude -p --model "provider/model" "<prompt>"
    Runtime flags take priority natively, avoiding any file modification on disk.

3. Pure Data Staging vs. --net=host

How should auth credentials pass into the container?

  • In corporate environments, --net=host is often blocked by security policies (CIS benchmarks). Also, OAuth localhost browser redirects fail across WSL2 and macOS VM boundaries.
  • Decision: No --net=host. Authentication is extracted on the host and copied via single-direction docker cp with restricted permissions (UID 10001:10001, mode 0600). The container runs inside a standard isolated bridge network.

4. Linux Kernel Read-Only Spec Lock (chmod 0444)

In Part 1, I introduced the spec-tamper rule to prevent agents from editing specs during implementation. In the container runner, this is enforced at the Linux kernel file system level:

  flowchart TD
    subgraph KERNEL ["Linux Kernel File System"]
        FILE["openspec/changes/&lt;name&gt;/specs/spec.md"]
        PERM["Ownership: root:root (0:0)<br/>Permissions: -r--r--r-- (0444)"]
        AGENT["Agent Process<br/>(UID 10001:10001, No Sudo)"]
    end

    FILE --- PERM
    AGENT -->|"Write / Edit Attempt"| PERM
    PERM -->|Permission Denied| FAIL["🚫 Hard Kernel Block (OS Level)"]

Before --stage apply starts, the container root script runs chown -R 0:0 specs/ and chmod -R 0444, then drops permissions permanently to unprivileged UID 10001. Even if an agent runs sed -i to change a test expectation in the spec, the Linux kernel rejects it with Permission denied.
